# Public profile tier parity

Use this rule whenever a product has public user, creator, performer, business, seller, provider, host, supplier, or other profile pages.

## Governing rule

If a profile is intentionally public and otherwise eligible for publication, its baseline discoverability and presentation quality must not depend on whether the owner uses a default, free, paid, partner, premium, or custom plan.

Paid or special tiers may add optional capabilities such as richer layouts, additional media, analytics, workflow tools, custom domains, automation, commerce features, or extra customization. They must not buy the basic right to be discoverable.

## Tier-neutral public baseline

Every eligible public profile should receive the same baseline treatment where the platform supports that surface:

- one stable canonical public URL;
- crawlable first-response content instead of JavaScript-only identity;
- index/follow eligibility under the same publication and safety policy;
- sitemap/search-directory eligibility under the same non-commercial rules;
- structured entity identity appropriate to the profile type;
- useful title, description, public name, role/type, and owner-approved public facts;
- internal links from relevant discovery/category/location surfaces where truthful;
- consistent mobile, accessibility, loading, empty-state, and error-state quality;
- social/share metadata and machine-readable guidance where the platform uses them;
- freshness/update evidence where available;
- no artificial ranking demotion or omission solely because the profile is default/free.

Do not treat a premium visual template as permission for a stronger canonical/indexing/search identity than a default template. A premium profile may look richer; a default public profile must still look intentional, complete, trustworthy, and usable.

## Default and custom are different acceptance contracts

Determine whether the requested artifact is the platform's default public profile, an owner-approved custom profile, or part of a named trade ecosystem before choosing its layout and proof. Default/free describes a platform baseline, not a lower quality bar. Every eligible public profile inherits the tier-neutral discovery and core-quality baseline above.

A custom profile additionally carries its approved reference, layout, real identity and content, interactions, and complete intended user journey. A generic profile can meet the common baseline yet fail the custom request. A trade-specific ecosystem may reuse profile infrastructure, but its own actors, services, relationships, and connected workflows determine acceptance; do not merge products with similar names or borrow another product's decisions. Compare the rendered artifact and actual workflow with approved evidence. If a reference cannot be obtained, preserve known requirements and mark visual fidelity unproved rather than inventing a match or treating the default template as approved. Essential custom behavior belongs in the first useful deliverable, not an unspecified polish phase.

## Non-public status must be explainable

A public-capable profile that is not public must expose a specific reason to its owner or operator. Valid reasons can include:

- owner selected private, draft, or unlisted;
- explicit publication/release step not completed;
- no supported public profile exists for that account role;
- unclaimed profile or missing owner authority;
- inactive, deleted, suspended, or moderation-blocked state;
- invalid or conflicted public handle/slug;
- missing minimum public identity or meaningful profile content;
- business ownership/trust/verification requirement not satisfied;
- regulated professional approval not satisfied;
- deliberate direct-link-only/review-only state;
- legal, privacy, safety, or integrity restriction.

Free, default, unpaid, not premium, not partner, missing subscription, or missing payment are never valid reasons for withholding the baseline public discovery surface.

If a product intentionally keeps an account class private, say that explicitly. Do not silently create a public page, and do not describe the absence as a paid-tier limitation.

## Verification

When auditing or changing public profiles:

1. Compare default/free and paid/premium public profiles against the same baseline checklist.
2. Search publication, sitemap, search, ranking, canonical, schema, and SSR logic for billing/subscription/partner/tier dependencies.
3. Confirm premium-only code changes optional capabilities rather than baseline discovery.
4. Inspect every non-public decision path and map it to a concrete owner-visible reason.
5. Treat unexplained non-public state or paid-tier discovery advantage as product drift.
6. Verify with real rendered/public responses where available; source contracts alone are not live acceptance.
7. For custom work, test both the shared public baseline and the distinct approved layout, content, actions, and end-to-end journey; passing the baseline alone does not establish bespoke acceptance.
